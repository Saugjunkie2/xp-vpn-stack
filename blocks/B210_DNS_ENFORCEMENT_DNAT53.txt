NOTES:
- DNS-Enforcement DNAT’t sämtlichen VPN-DNS (UDP+TCP/53) zwangsweise auf SERVICE_DNS.
  - Ziel v4: 10.77.0.1:53
  - Ziel v6: fd77:0:0:0::1:53
- Geltungsbereich (conn_group):
  - LEGACY: IPv4-only (kein v6 DNS/Traffic), DNAT53 gilt hier nur für v4.
  - ADMIN/MODERN: Dualstack (v4+v6), DNAT53 MUSS für v4+v6 aktiv sein (sonst DNS-Leak über v6 möglich).
- DNAT betrifft nur eingehenden VPN-Client-Traffic (Source ∈ VPN-Netze), unabhängig vom Tunneltyp (ppp* vs IKEv2/XFRM).
  - Server-eigene DNS Queries (OUTPUT) sind nicht Teil dieses DNAT und werden über lokale Resolver-Config gesteuert.
- Server-eigene DNS (OUTPUT) und interne Service-Upstreams ...(AdGuard → Unbound) dürfen nicht ungewollt mit umgebogen werden:
  exakte Match-Kriterien müssen deshalb Client-Source-Scope (VPN_Netze) + Excludes (Service-Net/lo/OUTPUT) verwenden.
================================================================================

1) ZWECK
- Redirect TCP/UDP 53 von VPN-Clients (Source ∈ VPN-Netze) zwangsweise auf SERVICE_DNS:
  - IPv4: 10.77.0.1:53 (LEGACY/ADMIN/MODERN)
  - IPv6 (nur ADMIN/MODERN Dualstack): fd77:0:0:0::1:53
- Gilt für ALLE VPN-Clients (auch restricted), damit DNS immer über AdGuardHome läuft – unabhängig vom Tunneltyp (ppp* vs IKEv2/XFRM).

2) GRENZEN
- Aktivieren erst wenn DNS stack stabil (B200).
- Dieses Enforcement betrifft NUR klassisches DNS über UDP/TCP Port 53.
  - DoH (HTTPS/443), DoT (TCP/853) und DoQ sind NICHT Teil dieses Blocks.
- Falls später ein "Total-DNS-Lockdown" gewünscht ist, ist das eine separate Outbound-Policy-Entscheidung (eigener Block/Decision).
- Dualstack-Parity (Kanon):
  - Dieser Block beschreibt DNS-Enforcement via DNAT53 für ADMIN/MODERN sowohl für IPv4 als auch IPv6.
  - LEGACY bleibt IPv4-only; daher existiert dort kein IPv6 DNS/Traffic, DNAT53 ist für LEGACY nur v4 relevant.
  - Konsequenz: Bei aktivem IPv6 (ADMIN/MODERN) ist DNAT53 für v6 Pflicht, sonst entsteht ein DNS-Leak-Pfad über IPv6.
- DNAT betrifft eingehenden VPN-Client-DNS-Traffic (UDP+TCP/53) unabhängig vom Tunneltyp:
  - LEGACY kommt typischerweise über ppp* (IPv4-only).
  - ADMIN/MODERN kann über IKEv2/XFRM/anderen Tunnel laufen (Dualstack).
- Match-Kriterium ist daher NICHT “Interface-Name”, sondern “Client-Source-Scope (VPN-Netze)”:
  - IPv4: Source ∈ {LEGACY_VPN_NET_v4, ADMIN_VPN_NET_v4, MODERN_VPN_NET_v4}
  - IPv6: Source ∈ {ADMIN_VPN_NET_v6, MODERN_VPN_NET_v6} (LEGACY bleibt v4-only)
- Server-eigene DNS Queries (OUTPUT) sind nicht Teil dieses DNAT und werden über lokale Resolver-Config gesteuert.
- Guard gegen “mit-umbiegen” von Server/Services erfolgt über Source-Scope (VPN-Netze) + explizite Excludes (Service-Net/lo), nicht über “ppp*”.

3) ABHÄNGIGKEITEN
- Requires: B200, B120, B150, docs/nft_service_ip_scopes.txt

4.1) NFTABLES (Kanon-Regelblöcke, konzeptionell; inet/nat)
Ziel:
- VPN-Clients (Source ∈ VPN-Netze): UDP/TCP 53 IMMER auf SERVICE_DNS umbiegen (tunnel-agnostisch):
  - IPv4 -> 10.77.0.1:53 (LEGACY/ADMIN/MODERN)
  - IPv6 -> fd77:0:0:0::1:53 (nur ADMIN/MODERN Dualstack; LEGACY bleibt v4-only)

Kanon-Regelblock (nftables):
- table inet nat
- chain prerouting { type nat hook prerouting priority dstnat; }
    - meta l4proto { udp, tcp } th dport 53 meta nfproto ipv4 ip saddr { LEGACY_VPN_NET_v4, ADMIN_VPN_NET_v4, MODERN_VPN_NET_v4 } dnat to 10.77.0.1:53
    - meta l4proto { udp, tcp } th dport 53 meta nfproto ipv6 ip6 saddr { ADMIN_VPN_NET_v6, MODERN_VPN_NET_v6 } dnat to [fd77:0:0:0::1]:53

Scope/Noise-Guard (MUST):
- Match basiert auf Client-Source-Scope (VPN-Netze), nicht auf iifname:
  • verhindert Drift zwischen Tunneltypen (ppp* vs IKEv2/XFRM).
- Excludes:
  • Service-Net (SERVICE_NET v4/v6) darf nicht als “Client” gematcht werden.
  • Local OUTPUT bleibt getrennt (Server-DNS/Upstreams werden via Resolver-Config gesteuert, nicht via DNAT).
- Nach DNAT ist es lokales Ziel (SERVICE_NET) => Enforcement liegt im filter input (B150 + docs/nft_service_ip_scopes.txt).

WICHTIG:
- Post-DNAT greift SERVICE_NET Input-Scope aus docs/nft_service_ip_scopes.txt (Least-Privilege).
- Restricted Allowlist (B150) muss DNS (tcp/udp 53) weiterhin erlauben, sonst bricht DNS-Enforcement im Restricted Mode.

5) OUTPUTS
- forced DNS
- Empfehlung (Kanon): Server nutzt Unbound direkt als Resolver (SERVICE_RESOLVER 10.77.0.2:53) statt AdGuard, um Abhängigkeiten/Loops zu minimieren; Client-DNS bleibt via DNAT immer AdGuard (SERVICE_DNS 10.77.0.1:53).

6) MUST (wenn aktiv)
- Both UDP and TCP 53
- Hook/Order: nft nat prerouting (DNAT) auf Client-Source-Scope (VPN-Netze) muss vor filter/input Enforcement greifen.
- Scope Klarstellung: DNAT betrifft nur eingehenden VPN-Client-DNS-Traffic (Source ∈ VPN-Netze); Server-DNS (OUTPUT) wird via lokaler Resolver-Konfig gesteuert (z.B. resolv.conf -> 10.77.0.2/Unbound).
- WICHTIG (Pfad nach DNAT):
  - Nach DNAT ist dst=10.77.0.1:53 => Traffic läuft über nftables filter input (lokales Ziel), nicht über forward.
- Daher MUSS Restricted Allowlist im input (B150 + docs/nft_service_ip_scopes.txt) explizit UDP+TCP 53 zu 10.77.0.1 erlauben, sonst bricht DNS-Enforcement (insbesondere im Restricted Mode).

7) OPTIONAL
- Kein nftables syslog logging fuer "external DNS attempts" (Noise/Logspam).
- DNS-Transparenz erfolgt ueber AdGuardHome Logs.
- Option B (Nice-to-have, Debug ohne Forensik):
  - Es duerfen Counters (aggregierte Pakete/Bytes) an den DNS-DNAT-Regeln vorhanden sein (UDP/53 und TCP/53 getrennt).
  - Keine Ziel-IPs/Domains/PII erfassen, keine syslog/kernel logs.
  - Zweck: Debug "Sendet der Client ueberhaupt klassisches DNS (Port 53)?" vs. "Problem nach DNAT (Input-Allowlist/DNS-Dienst/Upstream/MTU)".

8) FEHLERBILDER
- Some apps use DoH -> not covered by DNS enforcement (later policy decision).
- IPv6 DNS-Leak (nur wenn falsch konfiguriert): Wenn DNAT53 nur für v4 aktiv ist, können Dualstack-Clients (ADMIN/MODERN) DNS über IPv6 bypassen.
  Erwartung im Kanon: DNAT53 v4 + DNAT53 v6 sind aktiv und verifiziert (siehe Tests).
- MTU/Fragmentierung/EDNS0: grosse DNS-Antworten droppen (z.B. DNSSEC/EDNS0) -> DNS wirkt "kaputt", obwohl DNAT korrekt ist. Dann MTU/MSS/Fragmentation prüfen (B090 Kontext).

9) TESTS
- Client set DNS 8.8.8.8 -> still uses 10.77.0.1.
- TCP DNS Test: Client erzeugt DNS über tcp/53 (z.B. große Antwort / erzwungen) -> wird ebenfalls zu 10.77.0.1 umgebogen.
- Restricted Input Test:
  - Client ist restricted (Portal-Only) + setzt DNS manuell auf 8.8.8.8 -> DNS funktioniert trotzdem (DNAT auf 10.77.0.1:53) und input-allowlist lässt tcp/udp 53 zu.
- Negativtest (DoH): Wenn ein Client ausschliesslich DoH nutzt, steigen UDP/TCP-53 Counters nicht (falls Option B aktiv) und DNAT greift nicht. Erwartung: klassisches DNS bleibt erzwungen, DoH ist out-of-scope.
- Optional Counter-Test (wenn Option B aktiv):
  - UDP/53 Counter steigt bei DNS-Queries.
  - TCP/53 Counter steigt bei TCP-DNS-Fallback.
- IPv6 DNS Test (ADMIN/MODERN): Client setzt IPv6 DNS (z.B. 2001:4860:4860::8888) -> Traffic wird dennoch zu fd77:0:0:0::1:53 umgebogen.
