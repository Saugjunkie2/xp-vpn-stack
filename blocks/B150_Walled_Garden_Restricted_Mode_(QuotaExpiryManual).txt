NOTES:
- Restricted Mode gilt pro betroffener Verbindung/Subaccount (pppX), nicht global für den ganzen Server.
- Kein externes Captive-Portal: Walled Garden ist ausschließlich intern im SERVICE_NET erreichbar (SERVICE_*), nie am WAN.
- ADMIN-Exemptions (Kanon):
  - conn_group=ADMIN ignoriert die user-spezifischen Restricted-Trigger: Quota, Expiry, UNCLAIMED_OVERDUE/Claim-Deadline, Customer-Walled-Garden.
  - ADMIN wird beim Erstellen neuer vpn_connection automatisch gebunden/claimed (kein UNCLAIMED Flow für ADMIN).
  - Ausnahme: Manual Restrict / Not-Aus gilt für ALLE conn_groups (inkl. ADMIN) und erzwingt restricted_effective=true.
- Dualstack-Parity (Kanon):
  - LEGACY ist IPv4-only.
  - ADMIN/MODERN sind Dualstack; Restricted Enforcement muss daher restricted_v4 UND restricted_v6 abdecken.
- Allowlist muss minimal bleiben (DNS/WEB/NTP/ICMP nur zu SERVICE_*); alles andere bleibt geblockt, inkl. DNS-Bypass.

1) ZWECK
- Wenn Restricted Mode aktiv ist (Quota / Expiry / Manual / UNCLAIMED_OVERDUE):
  - nur SERVICE_* Allowlist erlauben:
    - DNS ausschließlich zu SERVICE_DNS (10.77.0.1) (udp+tcp 53)
    - WEB/Portal ausschließlich zu SERVICE_WEB (10.77.0.3) (tcp 80/443)
    - NTP ausschließlich zu SERVICE_NTP (10.77.0.4) (udp 123)
    - ICMP optional nur zu SERVICE_WEB (10.77.0.3) (echo-request + replies)
  - Rest blocken (kein WAN, keine anderen VPN-Clients)
- Bootstrap/Self-Heal MUST: Auch im Restricted (insb. UNCLAIMED_OVERDUE) muss das Panel/Portal auf SERVICE_WEB 10.77.0.3:80/443 erreichbar bleiben, damit der User Verify+Claim durchführen und wieder in FULL kommen kann.
  - User bekommt klare Anweisung im Panel (Reason + Next Step)
- DNS ist im Restricted Mode zwingend erlaubt, weil das Panel/Portal in der Praxis über FQDN genutzt wird (z.B. vpn.status -> SERVICE_WEB 10.77.0.3).
  B210 erzwingt DNS-Port 53 (udp+tcp) per DNAT auf AdGuardHome, unabhängig von Client-DNS-Einträgen.
- Onboarding nutzt KEIN Gate#1/Gate#2 Restricted Enforcement mehr:
  - Email-Verifikation wird über Verify-Wall im Panel umgesetzt (B155/B280), nicht über nftables.

2) AKTIVIERUNG (WIE "RESTRICTED" TECHNISCH GREIFT)
- Restricted Mode wird pro zugewiesener VPN-IP enforced (nicht pro User-Agent / nicht per URL).
- Quelle der Entscheidung ist SQL (B050): restricted_effective + restricted_reason (Felder liegen an der Connection in SQL, siehe B055; server-managed, kein Panel-SoT).
- Enforcement Mechanismus:
  - nftables nutzt Sets mit allen aktuell restricted Client-IPs:
    - restricted_v4 (IPv4)
    - restricted_v6 (IPv6; nur relevant für ADMIN/MODERN Dualstack)
  - Wenn Client-IP im passenden Set ist:
    - nur SERVICE_* erlauben (Walled Garden):
      - DNS: SERVICE_DNS 10.77.0.1:53 (udp+tcp) und fd77:0:0:0::1:53 (udp+tcp)
      - WEB/Portal: SERVICE_WEB 10.77.0.3:80/443 / fd77:0:0:0::3:80/443
      - NTP: SERVICE_NTP 10.77.0.4:123 / fd77:0:0:0::4:123 (udp)
      - ICMP optional: nur zu 10.77.0.3 (echo-request + replies)
    - alles andere blocken (Full-Tunnel bleibt, aber Walled Garden)

2.1) nftables Hook-Placement + Reihenfolge (KANONISCH)
WICHTIG (Pfad-Trennung):
- Traffic zu SERVICE_NET / SERVICE_* (dst ∈ 10.77.0.0/28) läuft über nftables "input" (lokales Ziel), nicht über "forward".
- Daher MUSS Restricted Mode zweifach enforced werden:
  1) input (iif ppp*): nur Allowlist-Ports zu SERVICE_* erlauben, alles andere im SERVICE_NET droppen (z.B. SSH/DB/etc.).
  2) forward: sobald saddr in restricted_v4 ODER saddr in restricted_v6 -> WAN-Forward droppen; zusätzlich zu anderen VPN-Clients droppen (Peer-Isolation bleibt wirksam).
- Restricted Mode MUSS im nftables "forward"-Pfad vor dem normalen Full-Tunnel Forward (B120) ausgewertet werden.
- Begründung: Wenn B120 (Forward->WAN allow) vor dem Restricted-Check kommt, kann ein restricted Client trotzdem ins Internet.

Kanonische Reihenfolge im forward chain (High-Level):

0) Connect-Pending Gate (D1a, NO-UNPOLICED-WINDOW):
   - Wenn ip saddr @connect_pending_v4 => DROP (forward, egal wohin).
   - Set wird beim Connect sofort gesetzt (ip-up) und erst nach SUCCESS von vpn-policy-apply entfernt.
   - Zweck: verhindert Traffic-Leaks ohne „Default Restricted“ (D1b) und ohne Portal-Zugriff bei SQL-Ausfall.

1) ct state established,related accept
   - Performance-Reason: bleibt früh.
   - Wichtig: HARD CUT verhindert Established-Bypass (Conntrack-Flush bei Eintritt in Restricted; siehe 2.2 / B166).

2) Peer-Isolation Drop (B130) (user->user drop)

3) Restricted Enforcement (B150) (Forward-Pfad):
   -  Wenn saddr in restricted_v4 oder saddr in restricted_v6:
     - DROP Forward nach WAN/ens13 (kein Internet)
     - DROP Forward zu anderen VPN-Clients (Peer-Isolation bleibt wirksam)
   - Hinweis: Zugriff auf 10.77.0.1 (DNS/WEB/NTP/ICMP) ist Service-IP Zugriff und wird im INPUT-Pfad geregelt
     (siehe 2.3 Restricted Allowlist + nft_service_ip_scopes.txt).

4) Normaler Full-Tunnel Forward + NAT (B120) für nicht-restricted Clients

2.1.1) NFTABLES PRIMITIVE (Sets, konzeptionell)
- restricted_v4: type ipv4_addr (dynamisch aus SQL-Truth gepflegt)
- restricted_v6: type ipv6_addr (dynamisch aus SQL-Truth gepflegt)
- Anwendung:
  - input chain (SERVICE_NET dst): allowlist nur SERVICE_* Ports (docs/nft_service_ip_scopes.txt), sonst drop
  - forward chain (WAN egress): wenn saddr ∈ restricted_v4 oder saddr ∈ restricted_v6 => DROP (kein Internet)

2.2) ENFORCEMENT-VERHALTEN (HARD CUT, "IMMEDIATE" DEFINITION)
- Der Wechsel in den Restricted Mode (egal aus welchem Grund: QUOTA / EXPIRY / MANUAL / UNCLAIMED_OVERDUE) ist ein HARD CUT.
- ADMIN-Exemption (Kanon, verbindlich):
  - QUOTA / EXPIRY / UNCLAIMED_OVERDUE / kundengetriebene Restricted-Policies werden für ADMIN NICHT bewertet/ausgelöst.
  - Für ADMIN kann RESTRICTED nur durch MANUAL/Not-Aus gesetzt werden (Variante A).
- Bedeutung: Bestehende Verbindungen (ESTABLISHED Flows) dürfen NICHT weiterlaufen. Es gibt keine Grace Period für laufende Downloads/Streams.
- Scope: Der Hard Cut betrifft ALLE Verbindungen/States der Client-IP (auch solche, die im Restricted Mode prinzipiell erlaubt wären, z.B. DNS/Panel/NTP).
  - Begründung: Maximale Sicherheit + deterministisches Verhalten.
  - Erwartetes Verhalten: Erlaubte Services reconnecten automatisch und werden danach gegen die Restricted-Allowlist geprüft und zugelassen.
- Technische Umsetzung (verbindlich, siehe B166):
  - Beim Transition von UNRESTRICTED -> RESTRICTED wird nach dem Kernel-Enforcement (nftables/tc) primär der Conntrack-State der Client-IP gelöscht (bidirektional).
  - Falls Conntrack-Flush fehlschlägt oder unavailable ist, MUSS als Fail-Safe die PPP-Session der betroffenen aktiven Verbindung beendet werden (PPP Session Kill),
    damit der Hard Cut deterministisch erfüllt ist.
  - Dadurch kann "ct state established,related accept" nicht als Bypass wirken, obwohl es früh im Ruleset steht.
- Safety-Net (Drift-Fix): Wenn Reconcile eine zuvor nicht-restricted IP wieder als restricted erkennt (missed event),
  MUSS der Hard Cut für genau diese neu-restricted IP ebenfalls ausgelöst werden (B166; im Reconcile best-effort, aber verpflichtend zu versuchen).

2.3) Restricted Allowlist (KANONISCH, SERVICE_* ONLY)
Wenn saddr ∈ restricted_v4 oder saddr ∈ restricted_v6 gilt:

- ALLOW (SERVICE_*; v4/v6 parity):
  - DNS -> SERVICE_DNS (10.77.0.1 / fd77:0:0:0::1):
    - udp/53 + tcp/53
  - WEB/Portal -> SERVICE_WEB (10.77.0.3 / fd77:0:0:0::3):
    - tcp/80 + tcp/443
  - NTP -> SERVICE_NTP (10.77.0.4 / fd77:0:0:0::4):
    - udp/123
  - ICMP/ICMPv6 (optional):
    - echo-request an SERVICE_WEB (v4+v6) + dazugehörige Replies (Diagnose)

- DROP:
  - alles andere (insb. forward nach WAN/ens13 und zu anderen VPN-Clients)

Hinweis:
- DNS muss TCP+UDP erlauben (große Antworten/EDNS/Retry).
- NTP ist für XP/Cert/TLS Stabilität erforderlich.
- SERVICE_RESOLVER 10.77.0.2:53 ist server-only und darf von Clients NIE direkt erreicht werden (auch nicht im Restricted).
- DNS-Zwang (B210) ist kompatibel: DNAT muss udp+tcp 53 umfassen und auf ppp* in nat prerouting greifen; Restricted erlaubt DNS (udp+tcp 53) ausschließlich zu SERVICE_DNS 10.77.0.1.

2.4) Sync/Apply + Reconcile Safety-Net (KANONISCH)
- Sync/Apply (D1a, SQL-First, KEIN Default-Restricted):
  - Beim Connect (ip-up) MUSS die Reihenfolge strikt sein:
    1) CLIENT_IP_v4 -> connect_pending_v4 (DROP ALL forward) [VOR jedem SQL Zugriff]
       - Bei Dualstack conn_groups (ADMIN/MODERN): zusätzlich CLIENT_IP_v6 -> connect_pending_v6
    2) vpn-policy-apply (single apply) lädt effective Policy aus SQL und setzt nft state
       (z.B. restricted_* / full state / Hard-Cut falls nötig / etc.)
    3) NUR bei SUCCESS (Exit 0): CLIENT_IP_v4 aus connect_pending_v4 entfernen;
       bei Dualstack zusätzlich CLIENT_IP_v6 aus connect_pending_v6 entfernen.
    4) Bei TEMPFAIL_SQL/ERROR/TIMEOUT: FAIL-CLOSED => PPP Kill; connect_pending_* bleibt bis Cleanup bestehen.
  - restricted_v4/restricted_v6 werden ausschließlich nach SQL-Truth gesetzt (restricted_effective).
    Es gibt keinen „Default Restricted“ Fallback.
- Bei Statusänderungen über Panel (Claim/Unclaim/Quota/Expiry/Manual) MUSS ein Sync erfolgen,
  damit Wirkung sofort greift (HARD CUT: Enforcement setzen + Conntrack-State flush bei Eintritt in Restricted; siehe 2.2 und B166).
  - Hinweis: Verify-Wall (Email-Verify) ist App-Layer und KEIN Kernel-Restricted-Trigger; dafür ist kein nftables Sync nötig.
- Reconcile Safety-Net (Option B):
  - Zusätzlich MUSS ein periodischer Reconcile laufen (z.B. alle 5 Minuten), der den Restricted-Zustand aus SQL deterministisch neu aufbaut.
  - Ziel: Drift-Reparatur (wenn Hook/Panel-Trigger ausfällt), stale IPs entfernen, konsistenter Ist-Zustand.
  - Reconcile ist idempotent: wiederholtes Anwenden führt immer zum gleichen Ergebnis.

  - SERVICE_NTP 10.77.0.4 / fd77:0:0:0::4: UDP 123

- (explizit NICHT erlaubt): SERVICE_RESOLVER 10.77.0.2 / fd77:0:0:0::2: UDP+TCP 53 (server-only); SERVICE_SSH 10.77.0.5 / fd77:0:0:0::5: TCP 22 (admin-only)

  - allow only above
  - drop everything else to WAN

7) MUST (immer, da HARD Enforcement)
- Must be immediate HARD CUT (bestehende ESTABLISHED Flows werden beim Eintritt in Restricted terminiert; kein "Soft Cut").

8) OPTIONAL

9) FEHLERBILDER

10) TESTS
- Toggle expiry -> user gets portal instantly.
- Toggle back -> internet works immediately.
- Verify-Wall ist App-Layer (B155/B280) und unabhängig vom nftables-Restricted. Restricted wird durch manual_restricted (alle) + Quota/Expiry/Restricted-Policy/UNCLAIMED_OVERDUE (nur USER, conn_group != ADMIN) gesteuert.
- Quota reset/renew -> restricted Set wird entfernt -> Internet sofort frei.
- Ordering Test: Client-IP in restricted_v4 *oder* restricted_v6 -> darf NICHT über forward ins WAN; nur SERVICE_WEB (10.77.0.3 / fd77:0:0:0::3) + SERVICE_DNS (10.77.0.1 / fd77:0:0:0::1) + SERVICE_NTP (10.77.0.4 / fd77:0:0:0::4) erreichbar (ICMP/ICMPv6 optional nur zu SERVICE_WEB).
- Hard Cut (ESTABLISHED) Test: Starte einen laufenden Download (WAN) und setze dann restricted_effective=true (Quota/Manual/Expiry). Erwartung: Datenfluss wird SOFORT unterbrochen (Conntrack-Cut), aber DNS+Portal+NTP bleiben erreichbar (v4/v6).
- Restricted Allowlist Test: restricted client kann DNS (udp+tcp/53) + NTP (udp/123) + Portal (80/443) + ICMP/ICMPv6 zu SERVICE_WEB nutzen, aber NICHT ins WAN (v4/v6).
- UNCLAIMED_OVERDUE Test (nur USER): unclaimed_grace_until überschritten -> restricted. Erwartung: Nur Portal/DNS/NTP (v4/v6) erreichbar, kein WAN. (ADMIN sollte diesen Pfad nicht erreichen, da auto-gebunden.)
- Input-Pfad Test (lokale Services): restricted client darf NICHT auf andere Ports im SERVICE_NET zugreifen (auch nicht über v6):
  - darf NICHT auf 10.77.0.1:2000 (AdGuard UI)
  - darf NICHT auf 10.77.0.5:22 (SERVICE_SSH, admin-only)
  - darf NICHT auf 10.77.0.2:53 (SERVICE_RESOLVER/Unbound, server-only)
  Erlaubt sind nur: SERVICE_WEB 10.77.0.3/fd77:0:0:0::3:80/443 + SERVICE_DNS 10.77.0.1/fd77:0:0:0::1:53 (udp+tcp) + SERVICE_NTP 10.77.0.4/fd77:0:0:0::4:123 (udp) + ICMP/ICMPv6 optional zu SERVICE_WEB.
