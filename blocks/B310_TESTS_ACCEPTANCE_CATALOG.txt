## 1) SimUse atomic guard tests (D012: Model A Truth + Model B Guard)
- Two parallel logins for same vpn_connection_id / subaccount_login (AAA identity; claim_token is claim-only):
  - Expect exactly one ACCEPT, one REJECT/TEMPFAIL (policy-defined)
- Lock row exists in active_session_locks after ACCEPT (kurzlebiger Guard)
- Lock released on Accounting-Start (DELETE lock row)
- Lock TTL = active_session_lock_ttl_seconds (Setting; failsafe/validierung gemäß B057) gemäß B057:
  - Wenn Acct-Start nie kommt (simulate drop): Lock läuft nach ~active_session_lock_ttl_seconds ab
  - Danach darf ein erneuter Login nicht mehr am Lock scheitern
- No Takeover:
  - Wenn radacct Session offen ist (stop_time IS NULL) und Janitor nicht schließen darf -> REJECT, kein “takeover”
- Steps / Commands (Minimal, MUST):
  - Erzeuge 2 parallele RADIUS Access-Requests für dieselbe Identität (vpn_connection_id + subaccount_login identisch).
    - Beispiel (Server/Testhost): parallel `radclient`/`radtest` (oder äquivalenter Test-Client).
  - Verifiziere unmittelbar nach dem ersten ACCEPT den Lock-Eintrag in `active_session_locks`.
  - Erzeuge anschließend (a) Acct-Start sauber, (b) alternativ: simuliere “kein Acct-Start” (Accounting blockiert/Drop).
  - Für “No Takeover”: Stelle sicher, dass `radacct.stop_time IS NULL` und das Runtime-Mapping als VALID existiert (oder explizit “nicht schließbar” ist).
- Pass/Fail (MUST):
  - PASS: exakt 1x ACCEPT + 1x REJECT/TEMPFAIL (policy-defined), nie 2x ACCEPT für gleiche vpn_connection_id/subaccount_login.
  - PASS: Lock existiert nach ACCEPT; Lock wird bei Acct-Start deterministisch entfernt.
- PASS: Wenn Acct-Start nie kommt: Lock läuft nach Ablauf von active_session_lock_ttl_seconds ab (gemäß B057; inkl. failsafe/validierung dort); kein Dauerlockout.
  - PASS: Wenn radacct live (stop_time NULL) und nicht schließbar => Login REJECT (Fail-Closed), kein Takeover.
  - FAIL: Doppel-ACCEPT, Dauerlockout, oder Takeover trotz live Session.
- Artifacts (MUST):
  - DB: `active_session_locks` row (created/expired/deleted), `radacct` (stop_time), ggf. `radpostauth`/Auth-Log.
  - Logs: policy/AAA decision + janitor notes (nur soweit vorhanden).

## 1.1) Connect Gate (D1a) – No Unpoliced Window
- Setup: In ip-up oder vpn-policy-apply künstlichen Delay einbauen (sleep 10).
- Erwartung: Während connect_pending_v4 aktiv ist, ist Forward-Traffic (WAN) 0.
- Erwartung: Nach SUCCESS wird Gate entfernt und Policy gilt (restricted/full).
- Negativtest: policy-apply TEMPFAIL_SQL/Timeout -> PPP wird gekillt, Gate bleibt bis Cleanup, kein Leak.
- Steps / Commands (Minimal, MUST):
  - In `ip-up` oder `vpn-policy-apply` (Testmode) künstlichen Delay setzen (z.B. 10s) und eine neue Verbindung aufbauen.
  - Während `connect_pending_v4` aktiv: versuche gezielt WAN-Traffic (z.B. HTTP/ICMP) zu erzeugen.
  - Danach: SUCCESS erzwingen (Policy apply OK) und erneut WAN-Traffic testen.
  - Negativtest: Policy apply bewusst in TEMPFAIL (z.B. SQL down/Timeout) laufen lassen.
- Pass/Fail (MUST):
  - PASS: Während connect_pending aktiv ist: Forward/WAN Traffic = 0 (kein Leak).
  - PASS: Nach SUCCESS: Gate entfernt, Policy greift (full oder restricted wie Outcome).
  - PASS: Bei TEMPFAIL: PPP wird beendet; Gate bleibt bis Cleanup wirksam; kein unpoliced window.
  - FAIL: Traffic geht raus bevor Policy greift oder Gate bleibt nach SUCCESS fälschlich aktiv.
- Artifacts (MUST):
  - nftables counters/ruleset (Gate-Regeln + Zähler), conntrack/counters (optional),
  - Logs: “connect_pending set/unset”, policy-apply result.

## 1.2) IKEv2 Gate-0 (Server-Zertifikat/Trust) + Gate-1 (EAP-MSCHAPv2) – No Bypass (B059)
- Ziel: Beweist, dass Gate-0/1 sauber getrennt sind und es nie ein “unpoliced window” gibt.
- Setup (MUST):
  - ADMIN/MODERN Access-Path aktiv (IKEv2).
  - Gate-0 ist Trust auf Server-Zertifikat (Public CA); kein Client-Zertifikat.
  - Policy-Gate/Connect-Gate Mechanik wie im restlichen System (kein Sonderpfad).
- Tests (MUST):
0) Dual-Stack Inbound (IPv4 + IPv6):
   - Setup: Verbindung 1x über IPv4 (A-Record / v4-Path) und 1x über IPv6 (AAAA-Record / v6-Path) aufbauen.
   - Erwartung: Handshake/Connect funktioniert über beide Paths; Gate-0/1 Semantik identisch (kein Sonderpfad).
   - Fail: IPv6-Path kann nicht handshaken/verbinden (PH1 Dual-Stack-Inbound nicht erfüllt) oder Gate-0/1 Verhalten driftet zwischen v4/v6.
1) Untrusted/invalid Server-Zertifikat ODER FQDN/Hostname-Mismatch (Trust-Chain bricht):
   - Erwartung: Gate-0 FAIL → Tunnel kommt nicht stabil hoch (fail-closed).
   - Erwartung: keine erfolgreiche AAA/Auth-Phase, keine Policy-Apply.
2) Trusted Server-Zertifikat + falsches Username/Password:
   - Erwartung: Gate-0 OK, Gate-1 FAIL (EAP/RADIUS reject) → keine Policy/kein Internet (fail-closed).
3) Trusted Server-Zertifikat + korrektes Username/Password:
   - Erwartung: Gate-0 OK, Gate-1 OK → Policy apply deterministisch aus SQL; erst danach Traffic.
4) User/Pass Rotation:
   - Erwartung: new pass works, old fails; no stale bypass.

- Artifacts (MUST):
  - Logs: generische “cert verify failed” / “server auth failed” / “hostname mismatch” (ohne Secret/PEM), EAP FAIL/OK (ohne Enumeration-freundliche Details).
  - DB: radpostauth/radacct passend; Reason-Codes konsistent (TEMPFAIL_* separat).

## 1.3) Dualstack Slot-Mapping + Panel-Stats SoT (Thema I) (B061)
- Ziel: Beweist deterministische IP-Zuordnung (ip_slot → fixed_ip/fixed_ipv6) und korrektes Fail-Closed bei Exhaustion; Panel-ONLINE SoT ist Accounting, nicht strongSwan.

1) Determinismus IPv4 (MODERN/ADMIN)
- Setup: Eine vpn_connection (MODERN oder ADMIN) mit gesetztem ip_slot in DB (B055).
- Erwartung:
  - PPP/RADIUS liefert Framed-IP-Address == vpn_connections.fixed_ip (keine Random-Leases).
  - Reconnect 10x: fixed_ip bleibt identisch.
- Validierung:
  - RADIUS Logs + PPP assigned IP + DB fixed_ip matchen.
  - /diag zeigt ip_slot + fixed_ip stabil (B270/B061).

2) Determinismus IPv6 (nur wenn v6_addr_policy=FIXED_SQL)
- Setup: MODERN/ADMIN Connection mit v6_addr_policy=FIXED_SQL und Pool-V6 vorhanden (B060/B061).
- Erwartung:
  - fixed_ipv6 wird deterministisch aus ip_slot materialisiert und bleibt bei Reconnect stabil.
  - LEGACY (v6_addr_policy=NONE) hat fixed_ipv6 = NULL und erhält keine IPv6 Route/Addr im VPN.
- Validierung:
  - DB fixed_ipv6 + Client IPv6 + /diag fixed_ipv6 stimmen überein (wo aktiv).

3) Pool Exhaustion Fail-Closed
- Setup: Pool (z.B. ADMIN /24) nahezu voll; tail_reserve_slots aktiv (B061).
- Erwartung:
  - Neue Allocations für non-admin schlagen fail-closed fehl (PPP kommt nicht hoch / wird beendet).
  - Panel/Stats zeigt Ampel RED; allocatable berücksichtigt Tail-Reserve (B061).
- Validierung:
  - Apply/Reconcile logs zeigen „no slot available“ (ohne PII-Leak).
  - Kein „random fallback“ im PPP.

4) Tail-Reserve Break-Glass (ADMIN)
- Setup: Pool voll, aber Tail-Reserve vorhanden.
- Erwartung:
  - ADMIN Connection kann (wenn Regel/Override aktiv) Reserve-Slot erhalten; non-admin nicht.
- Validierung:
  - DB zeigt Slot in Reserve-Range; Changelog/Audit vorhanden; /diag sichtbar.

5) ONLINE SoT = Accounting (nicht strongSwan)
- Setup: Simuliere flap/ghost session (PPP down, strongSwan zeigt evtl. noch SA).
- Erwartung:
  - Panel ONLINE basiert auf RADIUS accounting + active_session_locks window (B055/B165/B061).
  - Janitor räumt Ghost states deterministisch (B168).
- Validierung:
  - ONLINE toggles korrekt nach online_window_seconds; strongSwan-status beeinflusst nicht die Truth-Anzeige.

3) Allocator Randomness (ip_slot Vergabe) (Thema C/B064 + B061)
- Setup: Erzeuge 50 neue vpn_connections (ip_slot NULL), identischer Pool (conn_group gleich), Provisioning/Apply ausführen.
- Erwartung:
  - ip_slot Zuweisung ist nicht „lowest available“ monotone Reihenfolge.
  - Keine offensichtliche Sequenz (.10/.11/.12…) als Default-Pattern; Verteilung wirkt random (CSPRNG).
  - Mapping bleibt sticky: nach Zuweisung bleibt fixed_ip bei Reconnect stabil (kein Lease-Chaos).
- Validierung:
  - DB: ip_slot Werte über die 50 Allocations sind nicht streng aufsteigend ohne Lücken (Anti-Order).
  - Reconnect 10x: fixed_ip bleibt identisch (B061 Determinismus bleibt gültig).

4) Quarantäne / Reuse-Guard (Thema C/B064)
- Setup: Connection entziehen (revoked_at setzen), QUARANTINE_DAYS aktiv, versuche Slot/IP sofort wieder zu vergeben.
- Erwartung:
  - quarantined IP/Slot ist nicht vergebbar, solange now < revoked_at + QUARANTINE_DAYS.
  - Failure Reason ist sichtbar (POOL_EXHAUSTED_OR_QUARANTINED), kein stiller Fallback.
- Validierung:
  - DB + /diag + counters: eindeutige Ops-Sichtbarkeit, keine „teilweise Provisionierung“ bei Fail.

## 1.4) Panel Admin: Promotion/Demotion (Role Change → Connection Re-Issue) (B280)
- Ziel: Beweist, dass Promotion Admin-Zugriff als NEUE ADMIN-Connections provisioniert und Demotion Admin-Traffic sofort beendet (DoD: kein Admin-Netz-Traffic nach Demotion).

1) Promotion erzeugt neue ADMIN-Connection (kein „Upgrade“ bestehender Connections)
- Setup:
  - Customer existiert, hat zunächst keine Admin-Role.
  - Es existieren bereits LEGACY/MODERN vpn_connections (optional).
- Aktion: Promotion (User → Admin) via Panel-Admin (Role=ADMIN) (B280).
- Erwartung:
  - Es werden neue vpn_connection(s) angelegt mit conn_group=ADMIN.
  - Bestehende LEGACY/MODERN Connections bleiben unverändert (conn_group bleibt wie zuvor).
  - IP-Zuordnung erfolgt aus Admin-Pool (B060).
- Validierung:
  - DB-Diff: neue Rows mit conn_group=ADMIN sichtbar; keine conn_group Mutationen an alten Rows.
  - /diag zeigt conn_group=ADMIN für diese Connections (B270).
  - RADIUS Auth/Accounting kann mit den neuen Credentials funktionieren (ohne Zugriff auf Admin-Netz vor tatsächlicher Aktivierung).

2) Demotion deaktiviert alle ADMIN-Connections + optional Hardcut
- Setup:
  - Customer hat Admin-Role und mindestens eine ADMIN-Connection.
  - Optional: eine aktive Session auf einer ADMIN-Connection.
- Aktion: Demotion (Admin → User) (B280).
- Erwartung:
  - Alle ADMIN-Connections des Accounts werden DISABLED:
    - status/effective_state=DISABLED
    - disabled_at gesetzt
    - revoked_at gesetzt (Quarantäne/Entzug-Marker)
  - Optional Hardcut: aktive Session endet sofort (kein „auslaufen bis Reconnect“).
  - Reconnect-Versuch: RADIUS reject (kein VPN/kein Admin-Traffic).
- Validierung:
  - DB: disabled_at + revoked_at gesetzt; conn_group=ADMIN bleibt als Klassifikation bestehen, aber Zustand ist DISABLED.
  - Accounting/Session: radacct zeigt Stop/Ende (falls Session aktiv war); /diag reflektiert DISABLED.
  - Netzwerk: kein Admin-Netz-Traffic möglich (siehe Test 3).

3) DoD-Test: Nach Demotion darf kein Admin-Netz-Traffic mehr laufen
- Setup: wie Test 2 (nach erfolgter Demotion).
- Erwartung:
  - Traffic zu Admin-Netzen/Scopes wird geblockt (Policy/Kernel/AAA – je nach Kanonpfad).
  - Kein „Restzugriff“ via bestehende Session oder DNS/Panel-Umwege.
- Validierung:
  - Connectivity-Checks zu Admin-Targets schlagen fehl.
  - Logs zeigen klaren Failure-Reason (z.B. DISABLED/Demotion), ohne PII-Leak.

## 1.5) nftables / Enforcement / Reachability / DNS / Egress / Anti-Scan (Thema F) (B063)

F-001 (DoD-Log-DoS Bounded):
- Setup: Erzeuge Scan/Flood Noise auf WAN (z.B. viele NEW UDP flows auf random Ports), parallel legit IPsec Handshake.
- Erwartung:
  - Logs bleiben bounded (CONN_NEW_LOG_RATE_PER_SEC greift), keine Disk-Full Situation.
  - counters/labels sind aussagekräftig (Scan Noise sichtbar ohne Spam).
- Validierung:
  - journal + logrotate bounded, “keine stille Degradierung” (B063 9.6).

F-002 (Anti-Scan ohne IKE-Bruch):
- Setup: Flood erzeugen (NEW), dann IKEv1/v2 handshake testen (UDP 500/4500 + ESP).
- Erwartung:
  - IPsec Handshake funktioniert weiterhin unter Last.
  - RateLimit/Drop betrifft Scan Noise, nicht erlaubte IPsec Flows.
- Validierung:
  - IPsec SA kommt hoch, keine “flapping” durch RateLimit (B063 9.1).

F-003 (Service-Net Allowlist Only):
- Setup: Client (LEGACY) versucht diverse Ports/Ziele in SERVICE_NET.
- Erwartung:
  - DNS/Web/NTP erreichbar (nur definierte Ports).
  - Alles andere zu SERVICE_NET: DROP.
- Validierung:
  - nft counters zeigen erlaubte vs geblockte Service-Targets (B063 9.2).

F-004 (DNS Fail-Closed / Kein Bypass):
- Setup: Client setzt DNS auf extern (8.8.8.8) + testet TCP/UDP 53, optional v6.
- Erwartung:
  - DNS wird erzwungen (DNAT/REDIRECT auf SERVICE_DNS), kein externer Fallback.
  - Bypass-Versuche sind sichtbar (rate-limited labels/counters).
- Validierung:
  - Kein NEW DNS Traffic zu extern, counters “DNS_*” sichtbar (B063 9.3).

F-005 (IPv6 Egress: Fail-Closed + NAT66, kein “IPv6-frei”):
- Setup: ADMIN/MODERN Dual-Stack aktiv; IPv6 Egress ist als NAT66/Masquerade modelliert (analog IPv4 MASQUERADE).
- Teiltests (MUST):
  1) Pre-Apply / PENDING:
     - Erwartung: IPv6 WAN Egress ist geblockt (fail-closed); kein “unpoliced window”.
     - Erwartung: counters zeigen deny/pending-block (wie Gate-Mechanik).
  2) Post-Apply / ACTIVE:
     - Erwartung: IPv6 WAN Egress funktioniert nach erfolgreichem Policy-Apply (NAT66/Masquerade aktiv).
  3) “Nicht frei” (Guard):
     - Erwartung: Kein “freies”/unpoliced v6 WAN Egress außerhalb der erlaubten Policy-Pfade (B063 9.4).
- Validierung:
  - Nachweis 1): Kein Traffic vor Apply (counters/logs).
  - Nachweis 2): Traffic erst nach Apply (counters/logs) + IPv6 Egress OK.

F-006 (PH1 Full-Tunnel E2E – keine Split-Leaks, v4 + v6):
- Ziel: Beweist Full-Tunnel (Default-Route über VPN) und dass v4/v6 Egress nur nach Policy-Apply möglich ist.
- Setup (MUST):
  - Ein Client verbindet (LEGACY/PPP oder ADMIN/MODERN/IKEv2).
  - Policy-Apply Outcome ist “FULL” (nicht restricted), damit Egress erlaubt ist.
- Teiltests (MUST):
  1) Pre-Apply / PENDING:
     - Erwartung: Kein WAN Egress (v4 und v6) bis Policy-Apply SUCCESS (fail-closed).
  2) Post-Apply / ACTIVE:
     - Erwartung: Default-Route läuft über VPN (Client sieht “Internet” nur via Tunnel).
     - Erwartung: v4 Egress OK; v6 Egress OK (Dual-Stack wie spezifiziert; NAT66/Masquerade aktiv, analog IPv4).
  3) No Split Leak:
     - Erwartung: Keine direkte WAN-Route am Client vorbei (kein “gleichzeitig VPN + direkt”).
- Validierung (MUST):
  - Routes prüfen (v4 + v6): Default-Route zeigt auf VPN-Pfad (PPP oder XFRM-Pfad/Child-SA, je nach Stack).
  - Egress prüfen (v4 + v6): “Public IP”/Egress-Nachweis zeigt Server-WAN, nicht Client-WAN.
  - Counters/Logs: “connect_pending set/unset” + “policy-apply SUCCESS” + danach erst Egress-Traffic sichtbar.

F-007 (PH1 Peer-Isolation – Client↔Client block (User-Netz), v4 + v6):
- Ziel: Beweist, dass User-Clients untereinander nicht kommunizieren können (Peer-Isolation), unabhängig von v4/v6.
- Setup (MUST):
  - Zwei User-Clients gleichzeitig verbunden (User-Netz).
  - Beide sind “ACTIVE” (Policy applied), damit es keine Verwechslung mit pending/fail-closed gibt.
- Tests (MUST):
  1) v4 Peer Traffic:
     - Erwartung: ClientA → ClientB (ICMP/TCP/UDP) ist geblockt.
  2) v6 Peer Traffic:
     - Erwartung: ClientA → ClientB (ICMPv6/TCP/UDP) ist geblockt.
  3) Control:
     - Erwartung: ClientA → WAN (erlaubter Traffic) funktioniert gemäß Policy, damit klar ist: “nur Peer ist geblockt”.
- Validierung (MUST):
  - Ping/ICMP (v4 + v6) FAIL zwischen Clients.
  - Optional: TCP connect (z.B. Port-Test) FAIL zwischen Clients.
  - nftables counters/logs zeigen Peer-Isolation-Drop (ohne PII/Leak).

F-008 (PH1 v4/v6 Parität nach Apply – Policy wirkt symmetrisch):
- Ziel: Beweist, dass eine Policy-Entscheidung (ALLOW/DENY) nach Apply nicht nur für IPv4, sondern auch für IPv6 gleich wirkt (keine Sonderpfade).
- Setup (MUST):
  - Ein Client “ACTIVE” mit definierter Policy (FULL oder RESTRICTED).
  - Testziele: ein IPv4-only Ziel und ein IPv6-only Ziel (oder dual-stack Ziel, getrennt v4/v6 getestet).
- Tests (MUST):
  1) Wenn Policy ALLOW (z.B. DNS/HTTP erlaubt):
     - Erwartung: Zugriff funktioniert sowohl via IPv4 als auch via IPv6.
  2) Wenn Policy DENY (z.B. HTTP gesperrt / restricted):
     - Erwartung: Zugriff scheitert sowohl via IPv4 als auch via IPv6 (kein “v6 bypass”).
- Validierung (MUST):
  - Gleiche Anwendung/gleicher Zweck, einmal über v4 und einmal über v6 testen (z.B. curl -4 / curl -6 oder äquivalente Methode).
  - nftables counters/logs zeigen konsistentes ALLOW/DENY für beide Stacks.

## 2) Stale sessions tests (Ghosts, D012)
- Simulate ACCEPT without Acct-Start (kritisch):
  - Erwartung: Lock läuft nach active_session_lock_ttl_seconds ab (Setting; Failsafe=20s) (kein Dauerlockout)
  - Erwartung: nächster Login scheitert nicht am Lock
- Simulate missing Accounting-Stop:
  - Erwartung: radacct kann “offen” bleiben -> Login ist zunächst REJECT (Fail-Closed)
  - Erwartung: Janitor (B168/B169) schließt nur, wenn kein VALID Runtime-Mapping existiert
  - Danach: Login succeeds
- Determinismus:
  - Janitor schließt nie eine live Session (VALID mapping vorhanden)
  - Locks werden deterministisch bereinigt (expires_at < NOW())
- Steps / Commands (Minimal, MUST):
  - “ACCEPT ohne Acct-Start”: Accounting-Start gezielt verhindern (z.B. Accounting-Port blockieren / Testmode drop) und Login auslösen.
  - “Missing Acct-Stop”: Session normal starten, dann Stop verhindern (kontrolliert) und anschließend Re-Login versuchen.
  - Janitor-Run auslösen (On-Demand oder Timer) und beobachten, ob nur schließbare Ghosts geschlossen werden.
- Pass/Fail (MUST):
  - PASS: ACCEPT ohne Acct-Start => Lock läuft nach ~TTL aus (TTL=active_session_lock_ttl_seconds gemäß B057; inkl. failsafe/validierung dort); kein Dauerlockout.
  - PASS: Missing Acct-Stop => Re-Login initial REJECT (Fail-Closed), danach SUCCESS erst wenn Janitor schließen darf (kein VALID mapping).
  - PASS: Janitor schließt niemals live Sessions mit VALID mapping; nur bereinigbare Ghosts.
  - FAIL: Takeover wird möglich, oder Janitor schließt live Sessions, oder Ghosts bleiben unendlich hängen.
- Artifacts (MUST):
  - DB: `radacct` (stop_time, mapping status), `active_session_locks` (expires_at),
  - Logs: Janitor decision (“closed” vs “kept open”) + reason.

## 3) E2E validation
- Run 50 parallel connect attempts:
  - No double-ACCEPT for same vpn_connection_id
  - No DB deadlocks
  - Mean time stable
- Steps / Commands (Minimal, MUST):
  - Starte 50 parallele Connect-Versuche (Testhost/Tooling oder orchestriert über dein Panel/Testharness).
  - Varianz: gleiche Connection mehrfach parallel + unterschiedliche Connections parallel.
  - Beobachte DB (deadlocks/timeouts) und AAA decisions.

- Pass/Fail (MUST):
  - PASS: Für gleiche vpn_connection_id/subaccount_login niemals 2x ACCEPT parallel.
  - PASS: Keine DB deadlocks (und keine “stuck locks” danach).
  - PASS: System bleibt stabil (keine eskalierende Latenz / keine Queue-Explosion).
  - FAIL: Doppel-ACCEPT, Deadlocks, oder Lock-Leichen nach Test.

- Artifacts (MUST):
  - DB/Logs: Deadlock-Logs (MariaDB), Auth-Log/Audit, `active_session_locks` “clean state” nach Test.

## 3.1) Admin Hardcut (D012)
- Setup: aktive Session (radacct stop_time NULL, pppX live)
- Admin triggert Hardcut im Panel:
  - Erwartung: Panel führt keinen direkten kill aus (Privilege Separation via sudo wrapper)
  - Erwartung: vpn-session-kill beendet Session technisch (pppd/xl2tpd), danach reconcile/policy-apply
  - Erwartung: Kein Zombie-Traffic (nft/tc sind nach reconcile konsistent)
  - Erwartung: radacct wird durch den Kill/Stop (oder spätestens Janitor) sauber geschlossen
  - Danach: Re-Login ist möglich (Fail-Closed bleibt erhalten, kein Takeover)
- Steps / Commands (Minimal, MUST):
  - Baue eine aktive Session auf (pppX live, `radacct.stop_time IS NULL`).
  - Trigger Hardcut via Panel (soll über sudo-wrapper/worker laufen, nicht direkt im Webprozess).
  - Verifiziere technisch: pppd/xl2tpd Session beendet; danach reconcile/policy-apply ausgeführt.
- Pass/Fail (MUST):
  - PASS: Panel führt keinen direkten Kill aus (Privilege Separation bleibt erhalten).
  - PASS: Session ist technisch tot (pppX down/pppd beendet); nft/tc konsistent (kein Zombie-Traffic).
  - PASS: `radacct.stop_time` wird gesetzt (durch Kill/Stop oder spätestens Janitor).
  - PASS: Re-Login möglich; kein Takeover und kein Leak.
  - FAIL: Session “lebt” weiter, Policy bleibt inkonsistent oder radacct bleibt dauerhaft offen.
- Artifacts (MUST):
  - System: `systemctl/journal` (hardcut worker), Prozess-/Interface-Status (pppX),
  - Netzwerk: nft/tc snapshot,
  - DB: `radacct` stop_time gesetzt + ggf. Audit-Event.


## 4) ONBOARDING / VERIFY-WALL / CLAIM (SECURITY-CRITICAL E2E)
- PENDING Customer (email_verified_at NULL):
  - Panel erlaubt nur /verify + /verify/resend (kein Zugriff auf Connections/Actions).
  - /claim muss abgewiesen werden (Customer nicht ACTIVE).
- ACTIVE Customer (email_verified_at gesetzt):
  - Claim mit korrekt eingegebenem claim_token (Server prüft gegen claim_token_hash) funktioniert.
  - Wrong-claim_token Versuche sind rate-limited; kein Enumeration-Leak (gleiche Fehlermeldung für „nicht existent“ vs „falsch“).
- First-Claim IP-Bind:
  - Request VPN-IP muss == fixed_ip der Ziel-Connection sein, sonst Claim fail.
- Panel Greeting / display_name (UI-only):
  - Wenn display_name gesetzt (<=40 Zeichen): Panel-Anrede nutzt display_name („Hallo <display_name>“).
  - Wenn display_name leer/NULL: Panel-Anrede fällt auf email zurück („Hallo <email>“).
  - Validation: 41 Zeichen display_name wird abgewiesen (freundlicher UI-Error).
  - XSS-Safety: display_name wird escaped gerendert (kein Script/HTML Execute).
- subaccount_login Format + Read-only:
  - Jede neu erzeugte Connection hat subaccount_login, das Regex ^vpn_[a-z2-7]{16}$ matcht.
  - Panel zeigt subaccount_login an, aber es existiert kein Edit-Flow; Update-Versuche (API/POST) werden serverseitig rejected/audited.
- conn_group SoT (No-Inference) — SECURITY-CRITICAL (B058):
  - Setup: conn_group=LEGACY, aber fixed_ip absichtlich auf eine ADMIN-range IP setzen (Manipulation / Fehlkonfig).
  - Erwartung: Segment/Scope bleibt LEGACY (keine „Range-Inference“); Admin-only Tools bleiben unerreichbar; /diag zeigt conn_group=LEGACY.
  - Fail: Zugriff auf Admin-only Tools gelingt oder Segment kippt aufgrund IP-Range.
- Verify (Panel) vs AAA (VPN AuthN) — Ebenentrennung (B058):
  - Setup: Kunde existiert, email_verified_at=NULL (unverified Panel-User), aber vpn_connection ist technisch gültig (status/AAA-Kriterien erfüllt).
  - Erwartung: Panel blockt Claim/Actions wie beschrieben; AAA-Entscheidung bleibt ausschließlich an vpn_connection/state/policy gebunden (keine implizite Verify-Kopplung).
  - Fail: Verify wird „heimlich“ zum VPN-Allow/Deny Schalter oder erzeugt Bypass/Leak.
- UNCLAIMED_GRACE / UNCLAIMED_OVERDUE:
  - Nach Ablauf unclaimed_grace_until: Internet gesperrt (restricted), Panel/Verify/Claim bleibt erreichbar.
  - Claim innerhalb claim_deadline hebt UNCLAIMED_OVERDUE sofort auf (restricted entfernt, sofern kein anderer Grund).
- Hard-Stop:
  - Nach claim_deadline: Connection wird DISABLED; RADIUS reject; Claim muss fehlschlagen (Hard Stop).
