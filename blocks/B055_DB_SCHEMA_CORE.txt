1) INHALT
================================================================================

## 1) Purpose
Define core DB schema for:
- customers (panel account)
- vpn_connections (device/subaccount)
- active_session_locks (atomic SimUse guard)
- plus minimal indices required for high-performance reconcile

## 2) Core Tables

### 2.1 customers
- id (PK)
- email (UNIQUE)
- password_hash (Argon2id)
- display_name (VARCHAR(40), NULL allowed; UI-only; Panel greeting; Fallback=email; output must be escaped)
- created_at
- email_verified_at (TIMESTAMP, NULL bis Verify erfolgreich; Customer ist erst danach ACTIVE)
- status (ENUM: PENDING | ACTIVE | SUSPENDED | DELETED)
- (panel-only meta)

Indexes:
- UNIQUE(email)

### 2.2 vpn_connections (pro Gerät / VPN-Client / Subaccount)
- id (PK)
- customer_id (FK, NULL bis Claim)
- subaccount_login (PPP/RADIUS Username; pro Gerät; UNIQUE; serverseitig generiert; niemals user-supplied; nicht-enumerierbar)
  - Format (kanonisch): "vpn_" + 16 Zeichen Base32 (Alphabet: a-z2-7)
  - Ziel: keine ableitbaren/fortlaufenden IDs (Enumeration verhindern)
- conn_group (ENUM: LEGACY | MODERN | ADMIN; NOT NULL)
  <-- Kanonische Connection-Klassifikation (Scope/Policy/Diag); SQL-first SoT; niemals aus IP-Ranges “ableiten/erraten”.
- subaccount_nt_hash (MSCHAPv2 Secret als NT-Hash; SoT; kein Klartext-SoT)
- v6_addr_policy (ENUM: NONE | FIXED_SQL; NOT NULL)
  <-- IPv6 Adress-Policy (SQL-first). LEGACY = NONE (v4_only). ADMIN/MODERN = FIXED_SQL (Dualstack), sofern Pool-V6 verfügbar (B060/B061).
- ip_slot (INTEGER; SoT; NULL bis Provisionierung)
  <-- Deterministische Slot-ID als Single Source of Truth für IP-Zuordnung: aus ip_slot werden fixed_ip (IPv4) und fixed_ipv6 (IPv6) materialisiert (B061).
- fixed_ipv6 (IPv6; materialisiert aus ip_slot, nur wenn v6_addr_policy=FIXED_SQL; sonst NULL)
- fixed_ip (IPv4; materialisiert aus ip_slot; PPP-IP; RADIUS Framed-IP-Address; stabil pro Connection; keine Random-Leases) (B061)
- disabled_at (timestamp, NULL bis DISABLED)
  <-- Setzen wenn status=DISABLED (z.B. Demotion/Manual/claim_deadline). Einmaliger Marker (kein History-Log; nur Zustand/Operability).
- revoked_at (timestamp, NULL bis „revoked“)
  <-- Entzug-/Quarantäne-Marker (z.B. Demotion/Hardcut-Pattern). Wird genutzt, um „aktive“ Zuordnungen von „revoked“ zu trennen (Bezug: B280/B061).
- status (ENUM: PREPROVISIONED | CLAIMED | DISABLED)
- claim_token_hash (UNIQUE) <-- Hash des Claim-Tokens (claim_token Klartext existiert nur auf Gerät/Sticker/Label; NIE für VPN-Login)
- claimed_at (timestamp, NULL bis Claim)
- unclaimed_grace_until (timestamp) <-- bis dahin FULL, danach UNCLAIMED_OVERDUE -> restricted
- claim_deadline (timestamp) <-- Hard-Stop: Default created_at + 180d (Claim möglich bis dahin, danach DISABLED)
- restricted_reason (ENUM: QUOTA | EXPIRY | MANUAL | UNCLAIMED_OVERDUE, NULL wenn unrestricted)
  <-- Kernel/nftables Effective Reason (Performance/Debug). Wird deterministisch durch Apply/Reconcile gesetzt (B166), niemals user-supplied.
- restricted_effective (BOOL/TINYINT; 1 wenn restricted_reason != NULL, sonst 0)
  <-- Performance-Flag: Fast Path ohne Join-heavy Evaluate. Wird nur vom Server gepflegt (B166), keine UI-Quelle.
- created_at
- updated_at

Indices:
- UNIQUE(subaccount_login)
- UNIQUE(claim_token_hash)
- INDEX status
- INDEX customer_id
- INDEX conn_group
- INDEX fixed_ip
- INDEX unclaimed_grace_until
- INDEX claim_deadline
- INDEX restricted_effective
- INDEX restricted_reason
- INDEX disabled_at
- INDEX revoked_at

### 2.3 active_session_locks
Atomic guard (Mutex) against SimUse race (radacct is Truth for “session active”, this table is NOT a session-state)
- id (PK)
- vpn_connection_id (FK vpn_connections.id)
- session_key (VARCHAR)  <-- rein diagnostisch (z.B. derived from NAS-IP-Address + Calling-Station-Id + username)
- acquired_at (DATETIME)
- expires_at (DATETIME)  <-- MUST: NOW()+<Lock-TTL> wobei <Lock-TTL> = active_session_lock_ttl_seconds (gemäß B057; inkl. failsafe/validierung dort)
- state (enum: held, released)  <-- OPTIONAL, DIAGNOSTIC ONLY (kein Lifecycle / keine Logikquelle)
- release_reason (nullable)     <-- OPTIONAL, DIAGNOSTIC ONLY

Constraints:
- UNIQUE(vpn_connection_id)  <-- SimUse=1 guard
- INDEX(expires_at)          <-- janitor scans

Kanonisches Verhalten (A+B):
- Acquire: authorize end -> INSERT lock (expires_at = NOW() + Lock-TTL; Lock-TTL = active_session_lock_ttl_seconds gemäß B057)
- Release: on Accounting-Start (radacct start) -> DELETE lock row
- Expired locks dürfen im Auth-Pfad ignoriert/gelöscht werden (idempotent); verhindern keinen dauerhaften Lockout.

## 3) Notes / Constraints
- vpn_connections.restricted_effective is the performance field (avoid join-heavy evaluate path).
- active_session_locks must be used by B056 (RADIUS schema mapping) + B310 (acceptance tests / SimUse atomic guard).
- Verify-Code (email_verify_code) ist NON-CORE transient Security State: Hash/TTL/RateLimit/Lockout in customer_email_verify (SQL-first), Schalter email_verified_at liegt in customers.


================================================================================
4) NON-CORE EXTENSIONS (SQL-FIRST SETTINGS REGISTRY, MUST)
================================================================================
Ziel: SQL-first Policy/Parameter sind referenzierbar und auditierbar (kein Drift von “losen Zahlen” in Text/Configs).
Diese Tabellen gehören NICHT in die Core-Tabellen customers/vpn_connections/active_session_locks, sondern sind bewusst separate Extensions.

A) settings_catalog (MUST, maschinenlesbarer Contract)
Ziel: Jeder Settings-Key ist definiert (Typ/Range/Fail-Verhalten/Override-Regeln), damit Code/Panel nie „raten“.
- key (PK, immutable, unique global)
- type / value_type (ENUM):
  { INT, FLOAT, BOOL, STRING, DURATION, CIDR, ENUM, JSON } (oder dein zulässiger Satz)
- scope_default (ENUM): { GLOBAL }
- allowed_override_scope (ENUM): { NONE, CUSTOMER, CONNECTION, BOTH }
- is_required (BOOL)
- range_min / range_max (nullable, type-konsistent) ODER validator (kanonisch, explizit)
- fail_class (ENUM): { FAIL_CLOSED, FAIL_SAFE_HARDCAP }
- policy_direction (ENUM): { TIGHTEN_ONLY, RELAXES_ACCESS }
  Norm: Fallbacks nur erlaubt, wenn fail_class=FAIL_SAFE_HARDCAP UND policy_direction=TIGHTEN_ONLY.
- failsafe_value_* / failsafe_hardcap_value (typed; nur wenn fail_class=FAIL_SAFE_HARDCAP)
- missing_behavior (kanonisch; siehe B057)
- invalid_behavior (kanonisch; siehe B057)
- description (admin-facing text)
- docs_anchor (Referenz in Kanon: B057)
- created_at, updated_at (audit)
Optional (OPTION):
- domain_key (Governance: Auswahl statt Freitext; siehe B057 13.9)

B) settings_global (MUST)
Norm: Baseline/Default-Values (Scope=GLOBAL). Keine Policy-Logik hier, nur Facts/Values.
- id (PK)
- key (FK -> settings_catalog.key)
- value_* (typed) ODER value_raw + strict coercion nach settings_catalog.type
- updated_at (timestamp)
- changed_by (admin_id / system_actor_id)
- comment (optional)
- change_reason (optional)

Constraints:
- UNIQUE(key)

C) settings_customer (OPTIONAL, wenn per Kunde/Account variieren soll)
- id (PK)
- customer_id (FK -> customers.id)
- key (FK -> settings_catalog.key)
- value_* (typed) ODER value_raw + strict coercion nach settings_catalog.type
- updated_at, changed_by, comment, change_reason

Constraints:
- UNIQUE(customer_id, key)

D) settings_connection (OPTIONAL, wenn per VPN-Connection variieren soll)
- id (PK)
- vpn_connection_id (FK -> vpn_connections.id)
- key (FK -> settings_catalog.key)
- value_* (typed) ODER value_raw + strict coercion nach settings_catalog.type
- updated_at, changed_by, comment, change_reason

Constraints:
- UNIQUE(vpn_connection_id, key)

Kanonische Validierung (MUST):
- Type/Range/Validator müssen deterministisch gegen settings_catalog erfolgen.
- allowed_override_scope ist Whitelist-basiert (Write wird abgelehnt, wenn der Key im Katalog nicht freigegeben ist).
- Missing vs Invalid + Fail-Verhalten (FAIL_CLOSED vs FAIL_SAFE_HARDCAP) ist Kanon (siehe B057).
