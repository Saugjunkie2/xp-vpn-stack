=== H) IKEv2 / Credentials / Gate-0 Server Certificate Trust Ops-Contract (Hybrid) ===

NX-01 — IKEv2 AuthN/Credential-Contract für ADMIN/MODERN (Hybrid Gate-0)
- Bezug: 2.1(d) “ADMIN/MODERN → IKEv2”
- Ziel: Für ADMIN/MODERN kein PSK mehr als Gate-0. Stattdessen Server-Zertifikat (Public CA Trust; konkret: Let’s Encrypt).
  Username/Password bleibt unverändert als Identitäts-/Policy-Gate (Gate-1).

- Norm (MUST):
  • Gate-0 (Tunnel/Server-Auth): IKEv2/IPsec authentifiziert den Server per X.509 Server-Zertifikat.
    - Client validiert Hostname (FQDN) + Chain gegen Trust Store (Public CA) oder optional per Pinning.
    - Es gibt KEIN Client-Zertifikat in diesem Modell.
    - Gate-0 ist Infrastruktur-Zugang (Server-Authentizität), niemals Identität/Policy-Key.
  • Gate-1 (Identität/Policy): Identität/Policy bindet an vpn_connection via connection_login (Username/Password),
    Enforcement via RADIUS/EAP. Gate-0 ersetzt nicht Gate-1.
  • ADMIN/MODERN: IKEv2 AuthN erfolgt über EAP-MSCHAPv2 (Username/Password via FreeRADIUS),
    damit das Credential-Prinzip identisch bleibt (nur anderer Träger als PPP).
  • LEGACY bleibt unverändert: IKEv1/L2TP Gate-0 = PSK (separat dokumentiert im Legacy-Teil des Kanons).
    Der PSK gilt NICHT für IKEv2 ADMIN/MODERN.

- Sicherheits-/Flow-Guarantees (MUST):
  • Untrusted/Invalid/Expired Server-Zertifikat → kein erfolgreicher IKEv2 Aufbau (fail-closed auf Gate-0).
  • Trusted Server-Zertifikat + wrong user/pass → IKEv2 AuthN (EAP) FAIL (Gate-1), kein Policy-Apply, kein unpoliced window.
  • Trusted Server-Zertifikat + correct user/pass → Tunnel + deterministisches Policy-Apply gemäß SQL (conn_group / settings).

- Storage / SoT (MUST):
  • Private Key + Zertifikat sind root-only auf dem Server.
  • Keine Zertifikats-/Key-Materialien in SQL/Panel/Logs.
  • Logs dürfen nur generische Reasons enthalten (z.B. „server auth failed“, „cert verify failed“, „EAP auth failed“),
    niemals Key/PEM/Secrets.

- Ops-Contract: Zertifikatserneuerung (MUST, ohne neue Außen-Ports als Dauerzustand)
  • Renewal ist Pflicht (kurzlebige Public-CA Zertifikate). Es muss einen dokumentierten Renewal-Mechanismus geben.
  • Der Renewal-Mechanismus darf das WAN-Minimal-Exposure nicht als Dauerzustand aufweichen:
    - Dauerhaft von WAN erreichbar bleiben nur die VPN-Endpunkte (UDP 500/4500 + ESP).
    - Wenn für Renewal temporär TCP/80 oder TCP/443 gebraucht wird, muss das als kontrollierter, begrenzter Wartungsweg beschrieben sein
      (zeitlich begrenzt + auditierbar), oder es wird ein Challenge-Verfahren genutzt, das keinen WAN-Listener benötigt.
  • Nach erfolgreichem Renewal: Reload/Restart der relevanten Komponente(n) (strongSwan), ohne Policy/AAA Drift.

- Abuse-/Fehlerszenarien (MUST):
  • Zertifikat abgelaufen → alle IKEv2 ADMIN/MODERN Verbindungen schlagen fehl (Gate-0). Das ist gewollt (fail-closed).
  • Chain/Hostname passt nicht zur FQDN → fail-closed.
  • RADIUS down → Gate-1 fail-closed (kein Policy-Apply).
  • Wiederholte Auth-Fails → Rate-Limit/Abuse-Schutz greift gemäß globalem Abuse-Konzept (B062/B063/B310), ohne Leaks.

18) IKEv2 Gate-0 Server-Zertifikat: DoD / Validierung (MUST)
- Validierung Gate-0:
  1) Client validiert FQDN/Chain erfolgreich → Gate-0 PASS (Voraussetzung).
  2) Manipulierte/untrusted Chain oder falscher Hostname → Gate-0 FAIL (kein erfolgreicher Aufbau).
  3) Expired Zertifikat → Gate-0 FAIL.
- Validierung Gate-1:
  4) Correct Gate-0 + wrong user/pass → EAP FAIL; kein Policy-Apply; kein Internet.
  5) Correct Gate-0 + correct user/pass → Policy-Apply deterministisch (SQL-first).
- Observability:
  6) Logs/Diag zeigen klare Reason-Codes (ohne Secrets/PEM); Admin kann unterscheiden: „Gate-0 fail“ vs „Gate-1 fail“.
- Regression:
  7) Legacy (IKEv1/L2TP PSK) bleibt unverändert funktionsfähig; keine Cross-Impact durch IKEv2 Änderungen.

EF-002 — IKEv2 Gate-0: Server-Zertifikat/Trust Ops-Contract ist FEST (Hybrid Gate-0)
Anker: NX-01 + „18) IKEv2 Gate-0 Server-Zertifikat: DoD / Validierung“
- Gate-0 für ADMIN/MODERN ist Server-Zertifikat/Trust (Public CA; konkret: Let’s Encrypt, oder optional Pinning), kein PSK.
- Gate-1 bleibt connection_login (User/Pass) via EAP/RADIUS (SQL-first).
- Secrets/Keys bleiben root-only, nie in SQL/Panel/Logs.
- Renewal ist Pflicht, ohne dauerhaft zusätzliche WAN-Ports offen zu lassen; Verfahren ist dokumentiert und auditierbar.
- DoD belegt Gate-0 fail-closed + Gate-1 fail-closed + Legacy unverändert.
