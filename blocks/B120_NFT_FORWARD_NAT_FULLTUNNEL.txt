TITLE: nftables Forward + NAT (Full-Tunnel)
VERSION: v2.0
DATUM: 2026-01-21
STATUS: ACTIVE
PRIORITY: MUST
REQUIRES: B060, B100, B110
INFLUENCES: alle
OWNER-INTENT: Full-Tunnel Routing/NAT sauber und deterministisch.
OWNER: Marco (Owner) + ChatGPT (Co-Architect)

NOTES:
- Baseline ist Full-Tunnel: VPN-Clients nutzen Server als Default-Gateway (NAT/Masquerade Richtung WAN).
- Kein Split-Tunnel in der Baseline; falls nötig, muss das als eigene Entscheidung/Block kommen.
- Achte auf Reihenfolge: Abuse-Blocks/Peer-Isolation vor NAT; MSS-Clamp muss hier technisch korrekt eingehängt werden.
================================================================================

1) ZWECK
- Erlaubt VPN subnets -> WAN und NAT.

2) GRENZEN
- Kein Forward zwischen User-Clients (handled in B130).
- Restricted Mode (B150) kann Forward zusätzlich reduzieren (Portal-Only).
- WICHTIG (Pfad-Trennung): Dieser Block beschreibt nur Enforcement im forward-Pfad (WAN/NAT).
  - Traffic zu lokalen Services im SERVICE_NET (dst ∈ 10.77.0.0/28) ist lokales Ziel => nftables filter input.
  - Diese lokalen Service-Scopes (SERVICE_DNS/SERVICE_WEB/SERVICE_NTP) müssen im input-Pfad separat enforced werden:
    via B150 + docs/nft_service_ip_scopes.txt (sonst bleiben lokale Ports offen).

- Wichtig: Restricted Enforcement (B150) muss im forward chain vor dem allgemeinen Forward-Allow (dieser Block) evaluiert werden (sonst Umgehung möglich).

- Konkret (Restricted im forward-Pfad):
  - Für saddr ∈ restricted_v4 ODER saddr ∈ restricted_v6 (B150) MUSS forward ins WAN (z.B. oif ens13) deterministisch DROP sein (kein Internet).
  - Es gibt im forward-Pfad keine „Portal/DNS/NTP-Ausnahmen“ zu SERVICE_* — denn SERVICE_* ist input, nicht forward.
- DNS-Enforcement (B210): DNAT für 53/udp + 53/tcp auf SERVICE_DNS
  - v4 Ziel: 10.77.0.1:53
  - v6 Ziel: fd77:0:0:0::1:53
  (DNAT passiert in nat prerouting; danach greifen input/filter/forward Pfade wie kanonisch beschrieben).

3) ABHÄNGIGKEITEN
- Requires: B060, B100, B110
- Influences: B130, B140, B150, B210

4) INPUTS
- VPN source ranges
- WAN: ens13
- ppp interfaces

5) OUTPUTS
- forward allow:
  - LEGACY_VPN_NET_v4  10.77.16.0/20      -> ens13
  - ADMIN_VPN_NET_v4   10.77.2.0/24       -> ens13
  - MODERN_VPN_NET_v4  10.77.32.0/20      -> ens13
  - ADMIN_VPN_NET_v6   fd77:0:0:2::/64    -> ens13   (Dualstack)
  - MODERN_VPN_NET_v6  fd77:0:0:32::/64   -> ens13   (Dualstack)
- conntrack allow for return traffic
- NAT:
  - IPv4: masquerade Richtung WAN (ens13)
  - IPv6: NAT66/masquerade Richtung WAN (ens13) für ADMIN/MODERN v6 (LEGACY ist v4-only)
  - IPv4: NAT44/MASQUERADE für LEGACY_VPN_NET_v4 + ADMIN_VPN_NET_v4 + MODERN_VPN_NET_v4
  - IPv6: NAT66/MASQUERADE für ADMIN_VPN_NET_v6 + MODERN_VPN_NET_v6 (LEGACY bleibt v4-only)
  - Prinzip: IPv6 wird “wie IPv4” behandelt (kein Sonderregime, gleiche Policy-Logik; nur Address-Family unterscheidet sich technisch)

5.1) NFTABLES (Dualstack NAT, konzeptionell; inet/nat)
Ziel:
- v4: masquerade wie bisher
- v6: NAT66 masquerade analog (Server hat natives IPv6; Clients bekommen feste ULA v6 und egressen über NAT66)

- NAT out ens13:
  - NAT44 / masquerade: LEGACY_VPN_NET_v4 + ADMIN_VPN_NET_v4 + MODERN_VPN_NET_v4
  - NAT66 / masquerade: ADMIN_VPN_NET_v6 + MODERN_VPN_NET_v6 (ULA; LEGACY bleibt v4-only)

5.1) NFT (Dualstack NAT, konzeptionell – inet/nat postrouting)
Ziel:
- v4: NAT44 masquerade wie bisher
- v6: NAT66 masquerade analog (ADMIN/MODERN Dualstack)
- Keine “IPv6 Sonderregeln” auf Policy-Ebene: gleiche Gate/Restricted/Isolation Logik, nur family-spezifische nft Matches.

Kanon-Regelblock (nftables):
- table inet nat
  - chain postrouting { type nat hook postrouting priority srcnat; }
    - oifname "ens13" meta nfproto ipv4 ip saddr { 10.77.16.0/20, 10.77.2.0/24, 10.77.32.0/20 } masquerade
    - oifname "ens13" meta nfproto ipv6 ip6 saddr @dualstack_v6_prefixes masquerade

Kanon-Primitive für v6 Prefixe (damit B061 “Pool-Prefix” sauber abbildbar ist):
- set dualstack_v6_prefixes { type ipv6_addr; flags interval; }
  - enthält die Pool-Prefixe der Dualstack conn_groups (ADMIN/MODERN), z.B. fd77:0:0:2::/64, fd77:0:0:32::/64
  - LEGACY-Prefixe sind NICHT enthalten (Legacy bleibt v4-only)

Kanon-Block (Beispielstruktur):
- table inet nat
  - chain postrouting (hook postrouting priority srcnat)
    - oifname "ens13" meta nfproto ipv4 ip saddr { 10.77.16.0/20, 10.77.2.0/24, 10.77.32.0/20 } masquerade
    - oifname "ens13" meta nfproto ipv6 ip6 saddr { fd77:0:0:2::/64, fd77:0:0:32::/64 } masquerade

Validierung (MUST):
- ADMIN/MODERN Client: v6 “what is my ip” zeigt Server-v6 (NAT66) und v6 routing funktioniert.
- DNS-Zwang gilt auch v6 (B210), sonst DNS-Leak möglich.

6) MUST
- Full-tunnel works: default route on clients points to PPP
- NAT correct
- D1a: Kein unpoliced window: Solange policy-apply nicht erfolgreich war, muss forward deny-all über connect_pending_v4 (und bei Dualstack conn_groups zusätzlich connect_pending_v6) greifen.

7) OPTIONEN
- Separate NAT policies per subnet if needed later.

8) FEHLERBILDER
- No internet: forward or nat missing
- Only some sites: MSS clamp missing

9) TESTS
- From client: traceroute shows server exit.
- IP check: public IP = server IP.
