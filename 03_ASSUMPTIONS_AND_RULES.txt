A) Systemannahmen
- Debian 13 minimal.
- WAN Interface: ens13 (bei Abweichung: in B060 + B100 + nftables/ethtool Defaults anpassen).
- IPv6 ist NICHT global deaktiviert:
  - ADMIN/MODERN sind Dualstack (IPv4+IPv6 ULA) gemäß B060 (fd77:0:0:2::/64, fd77:0:0:32::/64).
  - LEGACY bleibt IPv4-only (XP/Vista PPP).
  - Leak-Control ist Pflicht: WAN-IPv6 ist aktiv und muss egress/forward Policies so gesetzt, dass keine unbeabsichtigten IPv6-Leaks möglich sind (kein „stiller Split“).
  - VPN-Inbound ist dualstack für MODERN/ADMIN:
    - IKEv2 (UDP 500/4500 + ESP) ist inbound auf WAN über IPv4 UND IPv6 erlaubt (AAAA ist First-Class).
    - LEGACY bleibt IPv4-only (L2TP/IPsec XP/Vista).
  - IPv6 Egress (ADMIN/MODERN) ist bindend: v6 läuft via NAT66/MASQUERADE auf WAN (analog IPv4 MASQUERADE); keine „IPv6-Sonderbehandlung“ auf Policy-Ebene (B120).
  - fixed_ip ist NICHT optional: jede vpn_connection/Subaccount hat ip_slot als SoT; daraus werden fixed_ip (IPv4, immer) und fixed_ipv6 (für Dualstack) materialisiert; Änderung nur via Admin Re-Provision/Slot-Reassignment (B055/B061).

- SERVICE ist kein /32-Anker mehr, sondern SERVICE_NET:
  - SERVICE_NET_v4: 10.77.0.0/28 (Service-IPs .1 DNS, .2 Resolver/Unbound, .3 Web, .4 NTP, .5 SSH (admin-only), .10 PPP-GW-Anchor)
  - SERVICE_NET_v6: fd77:0:0:0::/64 (Service-IPs ::1 DNS, ::2 Unbound, ::3 Web, ::4 NTP, ::5 SSH (admin-only))
  - Bind-Regel: Services binden ausschließlich an SERVICE_* (nicht an WAN/0.0.0.0).

- VPN Pools (SoT, ersetzt „2 Netze fix“):
  - LEGACY_VPN_NET_v4: 10.77.16.0/20 (XP/Vista, L2TP/IPsec, IPv4-only)
  - ADMIN_VPN_NET_v4/v6: 10.77.2.0/24 + fd77:0:0:2::/64
  - MODERN_VPN_NET_v4/v6: 10.77.32.0/20 + fd77:0:0:32::/64
- Pro Gerät = eigener Subaccount (1 Kunde -> n Verbindungen). Pro Subaccount feste IP (Policy/Stats/QoS/Quota).

B) Sicherheitsannahmen
- XP ist potenziell kompromittiert -> Outbound Abuse Blocks sind Pflicht (min. SMTP + SMB/NetBIOS).
- User sollen sich nicht gegenseitig sehen -> Peer-Isolation Pflicht (User↔User DROP).
- ADMIN ist nicht “gleichwertig” zu MODERN/USER bzgl. QUOTA/EXPIRY/UNCLAIMED_OVERDUE:
  - conn_group=ADMIN wird beim Erstellen neuer vpn_connection automatisch gebunden/claimed (kein UNCLAIMED Flow für ADMIN).
  - QUOTA/EXPIRY/UNCLAIMED_OVERDUE sind USER-Trigger (conn_group != ADMIN); ADMIN bleibt davon ausgenommen.
  - Manual Restrict / Not-Aus gilt für ALLE conn_groups (inkl. ADMIN).
  - Baseline-Security (DNS-Zwang, Peer-Isolation, Outbound-Abuse-Blocks, Rate-Limits) bleibt auch für ADMIN aktiv.
- Server darf von außen nicht wie "Admin-Server" wirken -> WAN minimal offen (v4+v6):
  - Nur VPN-Inbound sichtbar: UDP 500/4500 + ESP (IKEv2 dualstack für ADMIN/MODERN; LEGACY v4-only).
  - Keine Web/SSH/DB/AdGuard UI auf WAN (weder IPv4 noch IPv6).
- Fail-Closed ist Pflicht:
  Wenn AAA/SQL/Policy nicht sauber evaluierbar ist, wird kein Zugriff gewährt (kein Break-Glass via VPN).
- DNS ist Sicherheits- und Support-Kern:
  DNS-ZWANG ist IMMER aktiv (MUST): klassisches DNS (Port 53, TCP+UDP) wird per DNAT von iif ppp* -> 10.77.0.1:53 (AdGuardHome) erzwungen.
  Optional (Nice-to-have): Counters-only auf DNAT53/Policy-Pfaden (Pakete/Bytes), keine Logs/Forensik.
  DoH/DoT wird in dieser Runde nicht behandelt (PARKED).
- Logging/Spool/Retention ist Hybrid (SQL-first + Physik):
  SQL-first Settings steuern Policy (Retention/Intervals), aber lokale Safety Ceilings (hard max bytes/age) sind bindend (Physik > Policy).
  Bei Ceiling Hit gilt MUST: Drop/Ring-Buffer (Drop Oldest) + Alert (keine Stop-Policy, keine Disk-Full Eskalation durch Logs/Spool).

C) Änderungsregeln
- Jede Änderung:
  1) neue Masterversion
  2) betroffene Blocks aktualisieren + Block-Changelog
  3) Master-Changelog aktualisieren
- Keine stillen Änderungen, kein “wir machen das später”, kein Umbau ohne Decision Record wenn es
  eine Architekturentscheidung ist (decisions/D00x).
- Keine Neuinterpretation: Begriffe/Regeln bleiben in ihrem Sinn stabil. Wenn sich Sinn ändert:
  explizit als Decision + Anpassung in Glossar/Blocks dokumentieren.
- Terminologie ist bindend: "Token" wird nie unqualifiziert verwendet.
  Zulässig sind nur: claim_token (Claim), csrf_token (Webpanel), session_token (Webpanel). "Token" allein ist verboten.
  claim_token ist Claim-only (Panel), nicht VPN-Auth.
- Begriffe sind fix: Customer/Benutzeraccount = Panel-Login; Subaccount = VPN-Login pro Gerät (umgangssprachlich "VPN-Client").
- “Zeilenfest”-Dateien werden nicht “frei umformuliert”. Aufbau/Format bleibt stabil, nur Inhalte werden
  versioniert angepasst.

D) Qualitätsregeln / Abnahme
- Jede MUST-Anforderung erhält Acceptance Criteria im Block (prüfbar, nicht “Gefühl”).
- Jeder Block hat Failure Modes + Diagnosepfad (Symptom → Ursache → Fix).
- Setup-Tool ist Teil des Produkts (kein “User klickt sich das zusammen”):
  - NAT-T Registry Fix (XP)
  - Zeitstrategie (Pre-Connect/ Post-Connect NTP)
  - CA Import (Windows Store + MyPal NSS)
  - Verbindung/Status/Diag Shortcuts
- “Restricted statt Reject” ist bindend:
  Quota/Expiry/Manual/UNCLAIMED_OVERDUE -> ACCEPT + restricted_effective + restricted_reason.
  Verify-Wall ist App-Layer (Panel) und KEIN Kernel-Trigger für restricted_effective.
  Reject nur für DISABLED/BANNED/Missbrauch.
- Deterministische Durchsetzung ist bindend:
  - ip-up/ip-down erzeugen Runtime-Mapping (/run/vpn-sessions/pppX.env)
    MUST enthalten: PPPD_PID + PPP_IF + START_TS (PID-Reuse Schutz) + VPN-IP/connection_id.
  - vpn-policy-apply setzt tc + nft restricted sets
  - Hard Cut (MUST): FULL -> RESTRICTED wirkt sofort, auch für ESTABLISHED Flows:
    Reihenfolge: (1) Enforce (nft/tc aktiv) -> (2) Conntrack-Flush (bidirektional src+dst) der Client-IP.
    Fail-Safe (MUST): Wenn Conntrack-Flush fehlschlägt -> PPP-Session kill über PPPD_PID (fail-closed).
  - Reconcile (<=5min) macht FLUSH+REBUILD (Drift-Schutz)
- Integritätsschutz Runtime-Mapping ist Pflicht:
  /run/vpn-sessions/ und Mapping-Dateien müssen root-only write sein (chmod/chown).
  Manipulation durch Web-User/Services ist auf Dateisystemebene auszuschließen.
- Simultaneous-Use=1 ist bindend UND muss lockout-sicher sein:
  Stale Sessions werden aktiv gelöst (Janitor + On-demand Cleanup im Login-Flow), nicht ignoriert.
- Lock-Contention Verhalten (ip-up) ist bindend:
  bounded retry/backoff im ip-up (kurzes, begrenztes Zeitfenster), danach fail-closed default bis apply.
  Wenn vpn-policy-apply nicht erfolgreich/zeitnah durchläuft, darf keine undefinierte Session Traffic führen (Session wird beendet).
