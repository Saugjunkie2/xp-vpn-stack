3) VPN INPUT SCOPE (filter input) — Ziel: dst ∈ SERVICE_NET
================================================================================
Grundregel:
- Für Zugriffe auf SERVICE_* gilt nftables filter input (lokales Ziel).
- Im Restricted Mode MUSS die Allowlist auch im input enforced werden (sonst bleiben lokale Ports offen).

3.1 USER (LEGACY + MODERN), NICHT restricted
ALLOW zu SERVICE_*:
- SERVICE_WEB (10.77.0.3 / fd77:0:0:0::3):
  - TCP 80
  - TCP 443
- SERVICE_DNS (10.77.0.1 / fd77:0:0:0::1):
  - UDP 53
  - TCP 53 (DNS TCP fallback)
- SERVICE_NTP (10.77.0.4 / fd77:0:0:0::4):
  - UDP 123

DENY zu SERVICE_*:
- SERVICE_DNS UI: TCP 2000 (AdGuard UI)  [verboten für USER]
- SERVICE_RESOLVER: UDP/TCP 53 zu 10.77.0.2 / fd77:0:0:0::2 MUSS blockiert sein (Clients dürfen Resolver nicht direkt erreichen)
- SERVICE_SSH: TCP 22 zu 10.77.0.5 / fd77:0:0:0::5 MUSS blockiert sein (SSH ist ADMIN ONLY)
- alle anderen lokalen Ports im SERVICE_NET (DB, phpMyAdmin, ssh, etc -> MUSS blockiert sein)

3.2 ADMIN (ADMIN_VPN_NET), NICHT restricted
ALLOW zu SERVICE_*:
- alles wie USER
- PLUS: SERVICE_DNS UI: TCP 2000 (AdGuard UI)  [ADMIN ONLY]
- PLUS: SERVICE_SSH (10.77.0.5 / fd77:0:0:0::5): TCP 22  [ADMIN ONLY]

DENY:
- SERVICE_RESOLVER bleibt für Admin ebenfalls server-only (kein Client-Access auf 10.77.0.2:53)
- alle anderen Ports im SERVICE_NET (insb. SERVICE_SSH tcp/22 -> MUSS blockiert sein)

3.3 RESTRICTED (egal ob LEGACY/ADMIN/MODERN, wenn saddr ∈ restricted_* Sets)
STRICT ALLOWLIST im SERVICE_NET:
- SERVICE_WEB (10.77.0.3 / fd77:0:0:0::3): TCP 80, TCP 443
- SERVICE_DNS (10.77.0.1 / fd77:0:0:0::1): UDP 53, TCP 53
- SERVICE_NTP (10.77.0.4 / fd77:0:0:0::4): UDP 123

STRICT DENY:
- TCP 2000 (AdGuard UI) bleibt ADMIN ONLY; restricted darf UI nie sehen
- SERVICE_RESOLVER (10.77.0.2:53) bleibt server-only; restricted darf es nie erreichen
- alle anderen Ports im SERVICE_NET (insb. tcp/22 SSH -> MUSS blockiert sein)

================================================================================
5) DNS ENFORCEMENT (DNAT53) — nat prerouting
================================================================================
Ziel:
- Client kann klassisches DNS nicht "wegkonfigurieren".
- Alle DNS Queries (UDP+TCP/53) aus den VPN-Segmenten werden auf SERVICE_DNS (10.77.0.1:53) umgebogen.

IPv4 Regel (KANONISCH):
- (VPN ingress) udp dport 53 -> dnat to 10.77.0.1:53
- (VPN ingress) tcp dport 53 -> dnat to 10.77.0.1:53

WICHTIG (Pfad nach DNAT):
- Nach DNAT ist dst=10.77.0.1:53 => filter input.
- Daher muss input-allowlist (Kapitel 3) UDP+TCP 53 erlauben (auch im Restricted Mode).

IPv6 Hinweis (Dualstack ADMIN/MODERN):
- Kanon: IPv6 ist global aktiv für ADMIN/MODERN; LEGACY bleibt v4-only.
- DNS-Enforcement wird family-parallel gespiegelt:
  - IPv4: DNAT UDP/TCP 53 -> 10.77.0.1:53
  - IPv6: DNAT UDP/TCP 53 -> fd77:0:0:0::1:53
- Zusätzlich gilt Full-Tunnel via NAT66/Masquerade für ADMIN/MODERN, damit IPv6 wie IPv4 Internet-Egress hat.
- Diese Matrix setzt die Scope-Erwartung; die konkreten DNAT53-v6 Regeln stehen in B210.

Server-eigene DNS Queries (OUTPUT):
- DNAT gilt nicht für OUTPUT.
- Kanon: Server/AdGuard sprechen Unbound als upstream; Clients sprechen via DNAT immer AdGuard (SERVICE_DNS).
